Exactly. **10-O should not start with E2E testing.** It should start with a **product-readiness/setup audit**, and anything the tenant cannot configure themselves must be built before we call the messaging flow testable.

The PRD already envisioned tenant-facing Meta OAuth, knowledge-base CRUD, follow-up configuration, notifications, and dashboard setup.  But it also explicitly put WhatsApp in Post-MVP, which we are now changing: **WhatsApp Business is MVP scope.**

# What we need before 10-O E2E

I would introduce a new gate:

## Phase 10-O — Messaging MVP Readiness

And split it into **five parts**, not four.

### 10-O.0 — Tenant Self-Service Readiness Audit

First, inspect the actual implementation and answer:

> **Can a brand-new tenant configure and operate the complete Flow B product from the UI/API without touching the database, `.env`, source code, or asking the developer to manually create records?**

We need to inspect:

### 1. Workspace/business setup

Tenant should be able to configure things such as:

```text
Workspace
├── Business name
├── Business description
├── Services / products
├── Pricing information
├── Service area
├── Business hours
└── AI-facing business context
```

Because the AI prompt is explicitly supposed to use tenant business context such as business name, pricing range, services and qualification context. 

---

### 2. AI agent setup

Tenant needs a real place to configure the AI agent.

At minimum:

```text
AI Agent
├── Enabled / Disabled
├── Agent name
├── Business context
├── Tone / response behavior
├── Qualification goals
├── Qualification dimensions
│   ├── Budget
│   ├── Timeline
│   ├── Fit
│   └── Authority
├── Human handoff behavior
└── Fallback behavior
```

Not necessarily an enormous prompt editor.

The important thing is that the tenant controls the **business-specific inputs**, while QualiFly owns the underlying AI orchestration.

---

### 3. Knowledge/RAG setup

Tenant must be able to say:

> "This is what my AI agent should know."

For example:

```text
Knowledge
├── FAQs
├── Pricing
├── Services
├── Policies
├── Documents
└── Website/business information
```

This already has a tenant-facing Knowledge area according to the Phase 9 verification, so we need to determine whether it is sufficient for the actual AI-agent setup or merely CRUD. 

---

The tenant needs something like:

# 5. Follow-up setup

The tenant must control the behavior we're going to test.

For example:

```text

Follow-up #2

Message: "Wanted to follow up..."

Follow-up #3
```

And:

```text

☑ Cancel pending follow-ups
```

The PRD explicitly describes configurable follow-up sequences and tenant customization.

# 6. Human/team setup

This is another important piece.

A tenant needs to be able to operate the handoff itself.

Something like:

```text

Owner
  └── Admin
       ├── Sales member
       ├── Sales member
       └── Sales member
```

And:

```text
Handoff settings

☑ Notify team when human requested
☑ Notify on high intent
☑ Notify on AI failure
```

Then:

```text

     ↓
Handoff
     ↓
Team inbox
     ↓
Claim
     ↓
Start
     ↓
Human reply
```

The existing handoff system already gives us a large portion of this runtime capability; the question is whether **a real tenant can configure and operate it without developer intervention**.

## The key principle I would lock now

> **A feature is not MVP-ready merely because its backend exists. It is MVP-ready when a tenant can configure it, connect it, operate it, and observe its lifecycle without developer intervention.**

That means our immediate next development phase should **not** be "Instagram E2E testing."

It should be:

> **10-O.0 — Tenant Self-Service & Messaging Readiness Audit**

Then:

> **10-O.1 — Build the missing tenant-owned setup/control plane**

Then real Instagram/Messenger testing.

Then WhatsApp implementation.

Then real WhatsApp E2E.

That will prevent us from spending time "testing" a system whose critical setup path isn't actually productized yet.
